# Database Schema Reference

This document describes Laravel Bookings' database structure as shipped in `database/migrations/*.stub`. Column lists, defaults, and constraints below are taken directly from those migration files — if you need the authoritative source, read the stubs themselves.

## Schema Overview

Laravel Bookings uses five core tables to manage booking functionality:

1. **bookable_resources** - Defines bookable entities
2. **bookings** - Stores booking records
3. **booked_periods** - Individual time slots within bookings
4. **bookable_plannings** - Availability rules and constraints
5. **bookable_relations** - Data-only relationships between resources (see below)

Four optional/upgrade migrations extend these tables — `update_bookable_plannings_add_source_columns`, `update_bookings_add_parent_booking_id`, `update_booked_periods_constraints`, and `update_bookable_plannings_add_indexes`. Their effect is folded into the column lists below; see [Migration Guide](migration-guide.md) for upgrade instructions on existing installations.

## Core Tables

### bookable_resources

Represents any entity that can be booked through a polymorphic relationship (`create_bookable_resources_table`).

```sql
CREATE TABLE `bookable_resources` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `code` varchar(60) NULL,
  `resource_type` varchar(255) NOT NULL,
  `resource_id` bigint unsigned NOT NULL,
  `min` int unsigned NULL,
  `max` int unsigned NULL,
  `max_nested` int unsigned NULL,
  `size` int unsigned NOT NULL DEFAULT 1,
  `is_visible` tinyint(1) NOT NULL DEFAULT 1,
  `is_bookable` tinyint(1) NOT NULL DEFAULT 1,
  `created_at` timestamp NULL DEFAULT NULL,
  `updated_at` timestamp NULL DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `bookable_resources_resource_type_resource_id_index` (`resource_type`, `resource_id`)
);
```

#### Column Descriptions

| Column | Type | Description |
|--------|------|-------------|
| `id` | bigint unsigned | Primary key |
| `code` | varchar(60), nullable | Optional free-form identifier |
| `resource_type` | varchar(255) | Polymorphic type (model class name, or morph map alias) |
| `resource_id` | bigint unsigned | Polymorphic ID (model instance ID) |
| `min` | int, nullable | Not enforced by the package's own booking logic — available for application-level use |
| `max` | int, nullable | Maximum concurrent **bookings**. `null` means unlimited, not "never bookable" |
| `max_nested` | int, nullable | Not enforced by the package's own booking logic — available for application-level use |
| `size` | int, default 1 | Resource capacity, checked by `HasSizeFeatures::ensureHasFreeSize()` |
| `is_visible` | boolean, default true | Filtered by the `visible()`/`hidden()` scopes |
| `is_bookable` | boolean, default true | Filtered by the `bookable()`/`unbookable()` scopes; `size()` returns `0` when `false` |

Only the `(resource_type, resource_id)` index is created out of the box — there is no separate index on `is_bookable` or `is_visible` alone. Add one yourself if your query patterns need it:

```sql
CREATE INDEX idx_bookable_resources_status ON bookable_resources(is_bookable, is_visible);
```

### bookings

Stores booking records with a polymorphic `booker` relationship (`create_bookings_table`, plus `parent_booking_id` from `update_bookings_add_parent_booking_id`).

```sql
CREATE TABLE `bookings` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `parent_booking_id` bigint unsigned NULL,
  `code` varchar(64) NOT NULL,
  `booker_type` varchar(255) NOT NULL,
  `booker_id` bigint unsigned NOT NULL,
  `label` varchar(255) NULL,
  `note` text NULL,
  `meta` json NULL,
  `created_at` timestamp NULL DEFAULT NULL,
  `updated_at` timestamp NULL DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `bookings_code_unique` (`code`),
  KEY `bookings_booker_type_booker_id_index` (`booker_type`, `booker_id`),
  CONSTRAINT `bookings_parent_booking_id_foreign` FOREIGN KEY (`parent_booking_id`) REFERENCES `bookings` (`id`) ON DELETE SET NULL
);
```

There is **no** `creator_id` or `relatable_type`/`relatable_id` column on `bookings`. The "related model" concept lives on `booked_periods` (see below), not on the booking itself.

#### Column Descriptions

| Column | Type | Description |
|--------|------|-------------|
| `id` | bigint unsigned | Primary key |
| `parent_booking_id` | bigint unsigned, nullable | Self-referencing FK for [related bookings](related-bookings.md); `nullOnDelete` |
| `code` | varchar(64) | Unique booking identifier, generated by the configured `BookingCodeGenerator` unless passed explicitly |
| `booker_type` | varchar(255) | Polymorphic type (who made the booking), written via `getMorphClass()` |
| `booker_id` | bigint unsigned | Polymorphic ID (booker instance ID) |
| `label` | varchar(255), nullable | Human-readable booking title |
| `note` | text, nullable | Additional booking notes |
| `meta` | json, nullable | Flexible metadata storage, cast to `AsArrayObject` on the model |

#### JSON Meta Field Structure

The `meta` field supports flexible data storage — there's no fixed shape, it's whatever your application puts there, e.g.:

```json
{
  "attendees": 5,
  "equipment": ["projector", "whiteboard"],
  "catering": true
}
```

### booked_periods

Individual time periods within bookings, supporting multi-slot reservations (`create_booked_periods_table`, with `starts_at`/`ends_at` made `NOT NULL` and the foreign keys changed by `update_booked_periods_constraints`).

```sql
CREATE TABLE `booked_periods` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `booking_id` bigint unsigned NOT NULL,
  `parent_id` bigint unsigned NULL,
  `bookable_resource_id` bigint unsigned NULL,
  `relatable_type` varchar(255) NULL,
  `relatable_id` bigint unsigned NULL,
  `is_excluded` tinyint(1) NOT NULL DEFAULT 0,
  `label` varchar(255) NULL,
  `starts_at` datetime NOT NULL,
  `ends_at` datetime NOT NULL,
  `timezone` varchar(255) NULL,
  `note` text NULL,
  `created_at` timestamp NULL DEFAULT NULL,
  `updated_at` timestamp NULL DEFAULT NULL,
  `deleted_at` timestamp NULL DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `booked_periods_booking_id_foreign` (`booking_id`),
  KEY `booked_periods_bookable_resource_id_starts_at_ends_at_index` (`bookable_resource_id`, `starts_at`, `ends_at`),
  CONSTRAINT `booked_periods_booking_id_foreign` FOREIGN KEY (`booking_id`) REFERENCES `bookings` (`id`) ON DELETE RESTRICT,
  CONSTRAINT `booked_periods_bookable_resource_id_foreign` FOREIGN KEY (`bookable_resource_id`) REFERENCES `bookable_resources` (`id`) ON DELETE SET NULL,
  CONSTRAINT `booked_periods_parent_id_foreign` FOREIGN KEY (`parent_id`) REFERENCES `booked_periods` (`id`) ON UPDATE CASCADE ON DELETE CASCADE
);
```

> On fresh installs these are the constraints from `create_booked_periods_table`. Existing installations upgrade through the `update_booked_periods_constraints` migration — see [Upgrading from 1.x](migration-guide.md#upgrading-from-1x) for the required NULL-cleanup step and SQLite caveat. `is_excluded`, `note`, `timezone`, and soft deletes (`deleted_at`) predate that migration and exist on every install.

#### Column Descriptions

| Column | Type | Description |
|--------|------|-------------|
| `id` | bigint unsigned | Primary key |
| `booking_id` | bigint unsigned | Foreign key to bookings table; `RESTRICT` on delete — deleting a booking with periods fails until they are removed explicitly |
| `parent_id` | bigint unsigned, nullable | Self-referencing FK for grouping periods; cascades on delete |
| `bookable_resource_id` | bigint unsigned, nullable | Foreign key to bookable_resources; `SET NULL` on delete — deleting the resource preserves booking history |
| `relatable_type` / `relatable_id` | polymorphic, nullable | Optional link to any model (e.g. the app-level "reservation" or "rental" record) |
| `is_excluded` | boolean, default false | When true, this period is excluded from occupancy counting by `CheckBookingOverlaps` and the availability scopes |
| `starts_at` / `ends_at` | datetime, NOT NULL | Period boundaries. Overlap checks are **inclusive**: `starts_at <= end AND ends_at >= start` |
| `timezone` | varchar, nullable | Free-form, not interpreted by the package |
| `note` | text, nullable | |

#### Performance Indexes

```sql
-- Essential for overlap detection (created out of the box)
KEY `booked_periods_bookable_resource_id_starts_at_ends_at_index` (`bookable_resource_id`, `starts_at`, `ends_at`);
```

### bookable_plannings

Defines availability rules (weekdays + a validity window) for resources (`create_bookable_plannings_table`, plus `source_type`/`source_id` from `update_bookable_plannings_add_source_columns` and the composite index from `update_bookable_plannings_add_indexes`).

```sql
CREATE TABLE `bookable_plannings` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `bookable_resource_id` bigint unsigned NULL,
  `source_type` varchar(255) NULL,
  `source_id` bigint unsigned NULL,
  `label` varchar(255) NULL,
  `monday` tinyint(1) NOT NULL DEFAULT 1,
  `tuesday` tinyint(1) NOT NULL DEFAULT 1,
  `wednesday` tinyint(1) NOT NULL DEFAULT 1,
  `thursday` tinyint(1) NOT NULL DEFAULT 1,
  `friday` tinyint(1) NOT NULL DEFAULT 1,
  `saturday` tinyint(1) NOT NULL DEFAULT 1,
  `sunday` tinyint(1) NOT NULL DEFAULT 1,
  `matching_strategy` varchar(255) NOT NULL DEFAULT 'all',
  `starts_at` datetime NULL,
  `ends_at` datetime NULL,
  `created_at` timestamp NULL DEFAULT NULL,
  `updated_at` timestamp NULL DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `bookable_plannings_resource_dates_index` (`bookable_resource_id`, `starts_at`, `ends_at`),
  CONSTRAINT `bookable_plannings_bookable_resource_id_foreign` FOREIGN KEY (`bookable_resource_id`) REFERENCES `bookable_resources` (`id`) ON DELETE CASCADE
);
```

All seven weekday columns **default to `true`** — a planning row with no explicit weekday values is open every day. There are no `available_from`/`available_to`/`available_on`/`unavailable_on`/`booking_starts_at`/`booking_ends_at`/`min_time_before_booking`/`max_time_before_booking`/`min_booking_duration`/`max_booking_duration` columns; none of those exist. Weekday matching (`matching_strategy`: `all` or `any`) and the `starts_at`/`ends_at` validity window are the only constraints the package itself understands — see `BookablePlanning::scopeWherePeriodIsValid()`.

> `bookable_plannings_resource_dates_index` is created directly by `create_bookable_plannings_table` on fresh installs; existing installations add it via the publishable `update_bookable_plannings_add_indexes` migration — see [Upgrading from 1.x](migration-guide.md#upgrading-from-1x).

#### Column Descriptions

| Column | Type | Description |
|--------|------|-------------|
| `id` | bigint unsigned | Primary key |
| `bookable_resource_id` | bigint unsigned, nullable | Foreign key to bookable_resources |
| `source_type` / `source_id` | polymorphic, nullable | Optional link back to the business model that owns this planning (rate, seasonal rule, ...) — see [Synchronization](synchronization.md) |
| `label` | varchar(255), nullable | |
| `monday` … `sunday` | boolean, default **true** | Which weekdays this planning applies to |
| `matching_strategy` | string, default `'all'` | `all` = every weekday touched by the period must be enabled; `any` = at least one must be |
| `starts_at` / `ends_at` | datetime, nullable | Planning validity window. `null` on either side means unbounded in that direction |

### bookable_relations

Links a parent `BookableResource` to child resources it depends on or bundles together (`create_bookable_relations_table`).

```sql
CREATE TABLE `bookable_relations` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `parent_bookable_resource_id` bigint unsigned NULL,
  `bookable_resource_id` bigint unsigned NULL,
  `is_required` tinyint(1) NOT NULL DEFAULT 0,
  `min` int unsigned NULL,
  `max` int unsigned NULL,
  `created_at` timestamp NULL DEFAULT NULL,
  `updated_at` timestamp NULL DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `bookable_relations_parent_bookable_resource_id_foreign` (`parent_bookable_resource_id`),
  KEY `bookable_relations_bookable_resource_id_foreign` (`bookable_resource_id`),
  CONSTRAINT `bookable_relations_parent_bookable_resource_id_foreign` FOREIGN KEY (`parent_bookable_resource_id`) REFERENCES `bookable_resources` (`id`) ON DELETE CASCADE,
  CONSTRAINT `bookable_relations_bookable_resource_id_foreign` FOREIGN KEY (`bookable_resource_id`) REFERENCES `bookable_resources` (`id`) ON DELETE CASCADE
);
```

There are no `parent_id`/`child_id`/`relation_type`/`metadata` columns and no built-in "relation type" enum (`dependency`/`exclusion`/`inclusion`/`substitution` are not a real concept in this package) — those column names belong to a different design than what's implemented.

**`bookable_relations` is data-only.** `is_required`, `min`, and `max` are stored and available for your application's own validation logic (e.g. "this room requires between 1 and 2 parking spots"), but **the package does not read or enforce these columns anywhere in `BookResource` or `CheckBookingOverlaps`**. If you need enforcement, implement it yourself — for example inside an `onBookingSaving()` callback — by querying `bookableRelations()` and checking related resources' availability with `ensureIsAvailable()`.

#### Column Descriptions

| Column | Type | Description |
|--------|------|-------------|
| `id` | bigint unsigned | Primary key |
| `parent_bookable_resource_id` | bigint unsigned, nullable | Parent resource |
| `bookable_resource_id` | bigint unsigned, nullable | Related (child) resource |
| `is_required` | boolean, default false | Data-only flag — not enforced by the package |
| `min` / `max` | int, nullable | Data-only quantity bounds — not enforced by the package |

## Relationships Diagram

```
bookable_resources (1) ←→ (∞) bookable_relations (data-only, not enforced)
        ↓ (1)
        ↓
        ↓ (∞) booked_periods
        ↓         ↓ (∞)
        ↓         ↓
        ↓         ↓ (1) bookings ←→ (∞) bookings   (parent_booking_id, self-referencing)
        ↓
        ↓ (∞) bookable_plannings

polymorphic relationships:
- bookable_resources → resource (any model)
- bookings → booker (User, Organization, etc.)
- booked_periods → relatable (optional relation)
- bookable_plannings → source (optional planning-source model)
```

## Indexing Strategy

### Created out of the box

These indexes already exist from the migrations — do **not** recreate them, the `CREATE INDEX` statements below will fail on a duplicate name:

```sql
-- Polymorphic relationship lookups
-- bookable_resources_resource_type_resource_id_index on bookable_resources(resource_type, resource_id)
-- bookings_booker_type_booker_id_index on bookings(booker_type, booker_id)

-- Period overlap detection (CRITICAL — this is what CheckBookingOverlaps relies on)
-- booked_periods_bookable_resource_id_starts_at_ends_at_index on booked_periods(bookable_resource_id, starts_at, ends_at)

-- Planning lookups
-- bookable_plannings_resource_dates_index on bookable_plannings(bookable_resource_id, starts_at, ends_at)
```

### Additional indexes you may want

Not shipped by the package — add them if your query patterns need them, and give them names that won't collide with the ones above:

```sql
CREATE INDEX idx_bookings_created_at ON bookings(created_at);
CREATE INDEX idx_bookable_resources_status ON bookable_resources(is_bookable, is_visible);
```

The package does not add any `CHECK` constraints (e.g. "`starts_at < ends_at`", "no self-referencing relation") beyond the foreign keys documented above. If your application needs that level of enforcement, add it at the application layer or via your own migration.

## Common Queries and Optimization

### 1. Find Available Resources

```sql
-- Optimized query to find available resources
SELECT br.*
FROM bookable_resources br
WHERE br.resource_type = 'App\\Models\\Room'
  AND br.is_bookable = 1
  AND br.is_visible = 1
  AND NOT EXISTS (
    SELECT 1 FROM booked_periods bp
    WHERE bp.bookable_resource_id = br.id
      AND bp.is_excluded = 0
      AND bp.starts_at <= '2024-12-25 17:00:00'
      AND bp.ends_at >= '2024-12-25 09:00:00'
  );
```

This mirrors what `BookableResource::scopeAvailableSlotForPeriod()` does (inclusive boundaries, `is_excluded` ignored), but without the `max` concurrency comparison — prefer the scope itself over hand-rolling this query.

### 2. Check Booking Overlaps

```sql
-- Find overlapping, non-excluded periods for a resource
SELECT bp.*
FROM booked_periods bp
WHERE bp.bookable_resource_id = ?
  AND bp.is_excluded = 0
  AND bp.starts_at <= ?  -- requested end time
  AND bp.ends_at >= ?    -- requested start time
  AND bp.booking_id != ?; -- exclude current booking if updating
```

**Required index:** `booked_periods_bookable_resource_id_starts_at_ends_at_index`

Note this query only finds *rows* that overlap — `CheckBookingOverlaps` goes further and counts the highest number of *distinct bookings* concurrently active at any instant, so several rows from the same booking don't count more than once. See [Actions → Concurrency Semantics](actions.md#concurrency-semantics).

### 3. Resource Utilization

```sql
-- Calculate resource utilization
SELECT
  br.id,
  br.resource_type,
  br.resource_id,
  COUNT(bp.id) as booking_count,
  SUM(TIMESTAMPDIFF(MINUTE, bp.starts_at, bp.ends_at)) as total_minutes
FROM bookable_resources br
LEFT JOIN booked_periods bp ON br.id = bp.bookable_resource_id
  AND bp.starts_at >= '2024-12-01'
  AND bp.ends_at <= '2024-12-31'
GROUP BY br.id;
```

**Required index:** `booked_periods_bookable_resource_id_starts_at_ends_at_index`

This database schema provides a solid foundation for booking systems while maintaining flexibility for various use cases and ensuring optimal performance through proper indexing strategies.
